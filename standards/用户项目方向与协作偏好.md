# 用户项目方向与协作偏好

> 本文记录目前已经表达的长期方向与工作偏好。它是协作背景，不是对未来需求的永久限制；用户可以随时调整。

## 1. 总体方向

用户希望建立一套可跨项目复用的 AI 协作体系，而不是每个项目都从零设计工作流程。目标是让 AI 主动承担分析、规划、实施和审查工作，用户主要负责目标、关键决策、授权和最终验收。

## 2. AI 分工理念

- **Gemini 网页端 / Gemini App**：主要规划与核心产出者。利用可用的强模型完成项目分析、复杂技术方案、任务书初稿、核心代码、重构和技术解释。
- **ChatGPT GPT**：独立审核者。检查任务书、架构、代码、测试证据和交付质量；提供独立判断，不因模型间意见不同而机械否定。
- **Antigravity**：本地执行代理。适合处理下载后的文件、解压、整理、文件落位、本地构建/测试、Git 提交和推送等繁琐操作。其权限由具体项目手册约束。
- **用户**：项目最终决策者，控制重大方向、批准变更、接受交付和决定推进时机。

模型可用性、订阅权益和具体版本会变化；不要把某一时点可见的模型列表或限制写成永久事实。

## 3. 用户希望减少的手工工作

在适用的本地工作流中，用户希望避免反复手动解压、复制、整理文件、执行 Git commit/push。可以让本地代理在明确规则下处理这些步骤，并提供清晰回执。

用户仍希望保留对交付内容的可见性和最终决定权；自动化不能变成未经批准的产品决策或主分支变更。

## 4. GitHub 工作方式

- GitHub 是项目任务书、正式文档、代码和交付记录的长期载体。
- 任务书应能独立阅读，用户可以直接打开或下载后交给 Gemini。
- 交付要有任务编号、版本、分支、Commit SHA、文件清单和测试证据。
- 重要项目可以使用独立交付分支，GPT 审查后由用户决定是否合并。
- 具体项目可采用不同的文件夹语言和命名风格。用户偏好中文任务中心、任务书和交付说明；代码标识、路径和技术字段保留英文更清晰。

## 5. 项目类型

### 软件项目
重点关注需求覆盖、架构边界、兼容性、安全、可维护性、测试证据、可复现构建和 Git 追溯。

### 小说及创作项目
保留主创 AI 与独立审读 AI 的分工，但重点改为世界观、人物、剧情因果、时间线、文风、章节质量和文本连续性。

## 6. 沟通与推进偏好

- 使用中文沟通和撰写面向用户的任务文档；必要时提供英文对应版本。
- 直接说明结论、风险和需要用户决定的事项。
- 不要重复要求用户提供已经明确的信息或重复授权已获得的权限。
- 用户没有明确触发下一步时，不要自动开始下一轮审查、实施、合并或重大变更。
- 不要把建议写成已批准决定；把“已确认规则”和“待确认建议”区分开。
