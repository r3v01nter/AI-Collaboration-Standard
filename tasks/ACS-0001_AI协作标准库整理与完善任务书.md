## 1. 任务背景

用户希望建立一个跨项目通用的 AI 协作规范仓库，用来统一管理其软件开发、设备管理软件、小说创作及未来其他项目中的 AI 协作方法。

用户已提出《双 AI 协作工作规范 V1.0》：Google Gemini 作为项目规划与实施主力，ChatGPT GPT 作为独立审核与质量控制者，用户掌握最终决策权。后续讨论又明确了 Antigravity 的本地执行定位、任务书审核、交付证据、独立分支和用户批准门槛等机制。

当前仓库已经开始建立，但现有内容只是初步整理稿，不能视为最终定稿。Gemini 必须先检查仓库现状和本任务书，再提出完整整理方案。

## 2. 本项目的核心目标

把用户目前已经明确表达的协作理念、工作方法、项目方向和操作偏好，整理成一套：
1. 结构清晰、可长期维护的中央规范库；
2. 用户本人容易阅读、理解和修改的中文文档；
3. 便于其他 AI 阅读和执行的英文对应文档；
4. 能被不同项目仓库引用的通用标准；
5. 能直接复制使用的任务书、交付回执、审核报告等模板；
6. 能清楚区分用户已确认规则、AI 提出的建议、仍待用户决定事项的文档体系。

本任务不只是翻译现有 V1.0，也不是把所有聊天内容无差别堆进仓库。必须归纳、去重、分类、补齐结构，并保留信息来源和确认状态。

## 3. 用户已明确的核心方向

### 3.1 双 AI 分工

- Gemini 是项目规划与实施主力。应主动阅读项目仓库，分析项目现状，提出方向、技术方案、任务拆分，编写初版任务书，完成主要实现工作。
- ChatGPT GPT 是独立审核者和质量控制者。负责审核 Gemini 的项目分析、方案、任务书、代码、测试和交付；不应仅因方案与 GPT 偏好不同就否定合理方案。
- 用户是最终决策者。用户决定项目目标、重大方向、重要需求变更、最终验收以及是否进入下一阶段。
- GPT 不应在每轮验收后自动接管下一轮规划；默认应给出审核结论、问题和建议，再由 Gemini 提出下一轮方案，用户决定是否推进。

### 3.2 Antigravity 的定位

Antigravity 是可选的本地执行与交付代理，不是第三个产品决策者。可根据项目规则承担：
- 本地文件检查、解压、整理和应用；
- 本地构建、测试和调试；
- Git 分支、提交、推送；
- 整理交付回执和测试证据。

不得擅自改变用户需求、扩大范围、覆盖历史交付、强制推送或合并主分支。各项目应通过自己的操作手册定义其具体权限。

### 3.3 用户希望的协作流程

基本流程为：

1. Gemini 阅读项目仓库和项目规则。
2. Gemini 主动分析现状、问题和目标，提出规划。
3. Gemini 编写初版正式任务书。
4. GPT 独立审核任务书，指出缺陷、风险和需要补充的验收标准。
5. 用户决定是否批准任务书。
6. Gemini 按正式任务书实施并准备交付。
7. Antigravity（适用时）负责本地文件整合、构建测试和 Git 交付。
8. GPT 检查真实文件、分支、Commit、Diff 和测试证据，独立验收。
9. 用户决定是否接受、合并或进入下一阶段。

用户明确触发前，不应自动开始下一轮重大工作。

### 3.4 GitHub 与任务书

- GitHub 是正式任务书、项目规则、代码、交付记录和审查记录的长期载体。
- 用户希望能直接从仓库打开或下载任务书，再交给指定 AI 窗口执行。
- 任务书应明确任务编号、版本、目标仓库、当前基准、目标、非目标、实施范围、验收标准和交付要求。
- 重要交付应保留可追溯证据，包括分支、Commit SHA、文件清单、测试命令、测试结果和未完成事项。
- 推荐每轮使用独立交付分支；未经用户批准，不直接合并主分支。
- 不能把 AI 自称完成当作验收证据。

### 3.5 项目类型适配

软件开发项目重点审查需求覆盖、架构边界、代码质量、安全、兼容性、测试证据和可维护性。

小说及其他创作项目可以采用同样的主创 AI / 独立审读 AI / 用户决策者分工，但审查标准应改为世界观一致性、人物动机、剧情因果、时间线、文风、章节质量和文本版本管理，不得机械套用软件工程验收标准。

### 3.6 用户的实际使用偏好

- 面向用户的说明和任务书优先使用中文；英文版用于其他 AI 或跨语言复用。
- 用户偏好清楚的目录、中文任务中心和可直接阅读的任务书。
- 尽可能减少用户重复解压、复制、整理文件和手工 Git 操作，但自动化必须受项目规则约束。
- 需要把“已确认规则”“建议机制”“待用户决定”明确分开。
- 不要反复要求用户提供已经明确的信息，也不要把 AI 的建议写成用户已经批准的决定。

### C. 完善规范正文
至少明确：
- 三方核心分工：Gemini、GPT、用户；
- Antigravity 等本地执行代理的职责与边界；
- Gemini 主动规划、编写初版任务书和主要实施；
- GPT 独立审核、独立验收，不做无依据否定；
- 用户对需求、重大变更、不可逆操作和推进节奏的控制权；
- 任务书版本、基准 Commit 和适用范围；
- 独立交付分支、Commit、Diff、测试证据和回执；
- 缺陷分级、争议处理、退回修订和验收状态；
- 软件项目与创作项目的不同验收标准；
- 项目专属规则与中央通用规范之间的优先级；
- 新项目如何接入这套标准。

### D. 补充可复用模板
至少提供项目分析报告、正式任务书、交付回执、GPT 独立审查报告和项目专属规则模板。模板应可直接复制使用，不要只写概念介绍。

### E. 中英文一致性
中文文档作为用户主要阅读版本；关键规范应提供内容一致的英文版。英文版不能只是标题翻译，必须完整表达规则。模板可以先提供中文主版，再判断哪些确有必要提供英文版。

### F. 形成待确认事项清单
将所有尚未由用户明确决定的事项单独列出，例如：
- V1.1 中哪些新增治理机制正式成为强制规则；
- 是否所有项目都必须使用独立交付分支；
- 是否需要规定任务书和交付文件的统一语言；
- 中央规范版本升级和项目同步方式；
- 是否设置项目级例外及其批准流程。

不要擅自替用户作出上述决定。

6. 提交交付回执与证据。

如果实施中发现任务书自身存在冲突，先说明冲突和建议，不得自行扩大权限。

## 9. GPT 独立验收要求

本任务完成后，用户会将 Gemini 的交付结果交给 ChatGPT GPT 审查。GPT 应独立检查：
- 是否忠实保留用户已明确的协作理念；
- 是否把建议误写成已批准的强制规则；
- 是否完整覆盖用户方向、角色分工、工作流程和项目类型差异；
- 中文和英文是否实质一致；
- 模板是否可以直接投入使用；
- 文档是否互相矛盾、重复或缺乏可操作性；
- 仓库目录和 README 是否便于用户及其他 AI 使用；
- 交付是否有真实 Commit 和可核验文件。

GPT 不得仅凭 Gemini 的回执判定通过。若不通过，应列出具体文件、问题、依据和修订要求。
