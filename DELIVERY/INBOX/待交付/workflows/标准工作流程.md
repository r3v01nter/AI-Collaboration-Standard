# 标准工作流程

- 状态：通用流程（由中央规范库维护）
- 适用范围：所有接入 AI 协作标准库的项目
- 关联规范：[双 AI 协作与项目交付管理规范 V1.1](../standards/双AI协作与项目交付管理规范_V1.1.md)

## 端到端 11 步标准协作闭环

每一轮正式任务均按以下 11 个步骤推进，确保“规划有据、审核独立、交付可溯、决策归人”：

| 步骤 | 阶段名称 | 主导方 | 核心动作与产出 |
|---|---|---|---|
| **1** | **项目资料读取** | Gemini | 访问目标 GitHub 仓库（或本地交付包），读取 `README.md`、项目专属规则、当前任务入口及关键历史文件，记录基准 Commit SHA。 |
| **2** | **项目分析** | Gemini | 识别项目现状、已完成成果、现存缺陷、依赖关系与潜在风险；新项目接入时按 [项目接入与启动指南](项目接入与启动指南.md) 形成 [项目分析报告](../templates/项目分析报告模板.md)。 |
| **3** | **方案制定** | Gemini | 提出下一阶段目标、技术/创作方案、优先级、任务拆分与初版正式任务书（使用 [正式任务书模板](../templates/正式任务书模板.md)），单独列出假设与待决策项。 |
| **4** | **GPT 独立审核** | ChatGPT GPT | 独立审核方案与初版任务书：检查需求覆盖、逻辑一致性、风险与边界，补全可验证的测试矩阵与验收标准（使用 [独立审查报告模板](../templates/独立审查报告模板.md)）。 |
| **5** | **用户确认** | 用户 | 审阅规划、任务书及 GPT 审核意见，裁决重大争议，正式批准任务范围与授权边界。 |
| **6** | **正式任务书** | Gemini / 用户 | 固化经用户批准的正式任务书，标明任务编号、版本与「正式授权执行」状态，存入项目任务入口（如 `tasks/` 或 `任务中心/任务书/`）。 |
| **7** | **Gemini 实施** | Gemini | 严格对照正式任务书实施代码/文档/创作变更，执行本地自检或测试；若遇任务书与仓库事实冲突，立即暂停受影响部分并报告。 |
| **8** | **交付** | Gemini（+ Antigravity） | 将本轮全部成品与 `DELIVERY_REPORT.md` / [交付回执](../templates/交付回执模板.md) 统一打包为**单一 `.zip` 压缩包**交付用户；软件项目可由 Antigravity 协助解压落位、构建测试并提交独立交付分支，创作项目由用户检查后提交至 `inbox/gemini/待交付/`。 |
| **9** | **GPT 独立验收** | ChatGPT GPT | 检查真实仓库 Diff、Commit、待审目录文件与测试/自检证据，对照任务书逐项核验，给出「通过 / 有条件通过 / 不通过 / 证据不足」结论。 |
| **10** | **用户确认** | 用户 | 审阅独立验收报告与实际成果，决定是否接受交付、合并主分支或归档清理收件箱。 |
| **11** | **下一轮工作** | 用户触发 | 仅当用户明确发出下一轮指令后，由 Gemini 基于最新仓库基线开启新一轮规划；GPT 不自动接管下一轮规划。 |

---

## 不同项目类型的执行微调

- **软件工程项目**：第 7–8 步须附带真实构建与测试命令日志，推荐通过独立交付分支（如 `delivery/TASK-0001-R1`）提交审查；Antigravity 可在授权下承担本地测试与 Git 操作。
- **小说与创作项目**：第 7–9 步严格遵循 [创作项目协作规范](../standards/创作项目协作规范.md)，以世界观、人物、时间线与文本质量为验收核心，采用「单一 ZIP → 用户检查 → `inbox/gemini/待交付/` → 独立审读 → 归档」闭环，不强求 Gemini 直接写入 GitHub。
