# GitHub 交付与版本管理规范

- 状态：通用标准（由中央规范库维护）
- 适用范围：所有纳入 AI 协作体系的 GitHub 托管项目
- 参考实践：提炼自 `r3v01nter/Cultivation-Fantasy` 中文任务中心实践与软件工程分支交付实践

## 1. 设计原则

1. **GitHub 作为长期事实来源（Single Source of Truth）**：正式任务书、项目专属规则、源码/正文、交付记录与审查结论均以仓库记录为准。
2. **全程可追溯**：任何有效交付必须能够追溯到「任务编号 + 任务书版本 + 基准 Commit SHA + 交付文件清单/Commit SHA」。
3. **不强制一刀切**：不同项目可根据规模与性质选择「独立交付分支模式」或「中文任务中心 + 待交付收件箱模式」，不得强制所有项目都使用分支和 Pull Request。
4. **严禁编造或静默覆盖**：未实际推送到 GitHub 的文件不得声称已提交；无法获取 Commit SHA 时须如实标注；历史任务书与历史归档不得被静默覆盖。

---

## 2. 正式任务书存放与命名规范

### 2.1 存放路径
各项目可在以下两种入口中择一采用（并在项目专属规则中明确）：
- **中文任务中心模式**（推荐用于创作项目及中文主导项目，参考 `Cultivation-Fantasy`）：
  - `任务中心/README.md`：任务中心说明与项目专属协作流程。
  - `任务中心/当前任务.md`：指向当前唯一正在执行的任务入口与状态。
  - `任务中心/任务书/`：存放历次正式任务书原件，只增不覆。
- **标准英文任务目录模式**（适用于软件工程项目）：
  - `tasks/`：存放正式任务书（如 `TASK-0001_...md` 或 `ACS-0001_...md`）。

### 2.2 命名规范
正式任务书文件名须包含**任务编号/版本号**与**中文主题**，例如：
- `<任务编号>_<中文任务主题>任务书.md`（如 `ACS-0001_AI协作标准库整理与完善任务书.md`）
- `<版本号>_<中文任务主题>任务书.md`（如 `V6.9.1_第81章方案定点补正任务书.md`）

### 2.3 执行准绳
当仓库内存在多份历史任务书时，必须明确“当前唯一有效任务”（例如通过 `任务中心/当前任务.md` 或任务书头部的状态字段），防止执行 AI 误读过期版本。

## 3. 版本追溯与 Commit SHA 记录规则

1. **起始基准记录**：任何规划或实施启动前，执行 AI 应记录当前读取到的默认分支与最新 Commit SHA（完整 40 位或至少前 7 位短 SHA）。
2. **交付记录**：
   - 若通过 Git 分支直接提交，须在交付回执中记录：目标分支、基准 Commit SHA、交付 Commit SHA 及提交链接。
   - 若当前环境无 GitHub 写入权限（如网页端/沙盒端通过 ZIP 交付），**严禁编造 Commit SHA**，须在交付报告中如实注明“未直接提交 GitHub，以单一 ZIP 压缩包交付，待用户审核后提交”。
3. **历史不可篡改性**：已发布的任务书版本（如 V1.0）应保留原件或通过明确版本递增（V1.1、V1.2）及 `CHANGELOG.md` 记录变更，不直接销毁历史审计痕迹。

## 4. 交付文件管理与归档原则

### 4.1 单一 ZIP 压缩包交付（AI → 用户）
当 AI（如 Gemini）在网页端或独立沙盒完成多文件产出时：
- 必须将本轮全部新增/修改文件（含 `DELIVERY_REPORT.md` 或交付回执）按仓库相对路径打包为**唯一一个 `.zip` 压缩包**。
- 命名建议：`<任务编号>_<任务名称>_交付包.zip`。
- 禁止逐个发送散落文件，也不得把未修改的无关历史大文件重复塞入交付包。

### 4.2 项目级交付与归档模式（二选一）

#### 模式 A：独立交付分支模式（推荐用于中大型软件项目）
- 每轮任务从最新基分支切出独立分支（如 `delivery/TASK-0001-R1` 或 `feat/task-0001`）。
- 本地代理（如 Antigravity）或开发者解压交付包、运行构建/测试并推送该分支。
- GPT 独立审查该分支的真实 Diff、测试日志与文件内容。
- 用户确认验收后决定合并至 `main` 并清理分支。

#### 模式 B：收件箱待交付 + 人工归档模式（推荐用于小说创作与轻量项目）
提炼自 `Cultivation-Fantasy` 仓库的成熟实践：
- Gemini 打包交付物并发送给用户。
- 用户检查无误后，手动解压并提交至仓库暂存收件箱（如 `inbox/gemini/待交付/`）。
- GPT 针对 `inbox/gemini/待交付/` 中的真实文件执行独立审查。
- 审查通过并经用户确认后，由用户（或授权后的归档流程）将定稿移入正式目录（如正文/设定/规范目录），并清空 `待交付/`（仅保留 `.gitkeep`），进入下一轮循环。
- **保护红线**：不得强制要求主创 AI 直接向此类仓库执行 `git push`；不得覆盖冻结基线或历史归档。

---

## 5. 跨项目冲突与异常处理

- 若实施期间上游仓库基线发生变更（有新 Commit），执行 AI 或本地代理须先比对差异并报告，严禁直接强推（`git push --force`）或覆盖他人提交。
- 若发现任务书要求与仓库实际状态冲突，应暂停受影响部分，记录冲突事实并等待用户决策。
