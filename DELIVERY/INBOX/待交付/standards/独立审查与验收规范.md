# 独立审查与验收规范

- 状态：通用标准（由中央规范库维护）
- 适用范围：ChatGPT GPT（或其他指定独立审核 AI）对规划、任务书及交付成果的独立审查
- 配套指南与模板：[GPT独立审核指南](../workflows/GPT独立审核指南.md) | [独立审查报告模板](../templates/独立审查报告模板.md)

## 1. 核心原则

1. **证据驱动，拒绝轻信**：绝不允许仅凭执行 AI（Gemini）的口头总结、“我认为已完成”或无日志的“测试通过”声明判定验收通过。
2. **独立且客观**：不因任务已执行完毕而默认放行，也不得为彰显独立性而刻意挑刺或因个人技术偏好否定合理方案。所有缺陷与风险结论必须附带具体文件路径、行号/Diff、命令输出或逻辑依据。
3. **不越权接管**：GPT 负责审核与质量把关，验收结束后输出结论与待处理事项；除非用户明确要求，否则不自动接管下一轮整体规划。

---

## 2. 审查对象与核验内容

独立审查分为两个阶段：

### 2.1 阶段 A：规划与任务书审核（实施前）
- 核对是否已读取最新仓库基线。
- 检查目标、非目标、工作范围与禁止事项是否清晰无冲突。
- 检查验收标准是否可观察、可测试，补充遗漏的边界条件、安全/隐私控制或回归风险。
- 检查是否误将 AI 建议写成已确认需求。

### 2.2 阶段 B：交付成果独立验收（实施后）
必须逐项核验以下真实交付物（GitHub 分支/Commit/Diff、`inbox/gemini/待交付/` 或用户转发的完整 ZIP 交付包）：
1. **文件完整性**：对比任务书要求与交付包/Commit 文件清单，确认无缺失、无空文件、无重复垃圾文件。
2. **实际修改内容**：直接阅读关键文件内容或 Git Diff，核实功能、文档、链接、格式是否真正落地。
3. **测试与自检证据**：
   - 软件项目：核验实际执行的构建命令、测试命令、环境信息、原始日志及失败/跳过项说明，严格区分「已运行通过」「未运行」「环境受限无法运行」与「仅理论推理」。
   - 创作项目：核验世界观设定、时间线、人物状态、文风与连续性（详见 [创作项目协作规范](创作项目协作规范.md)）。
   - 规范/文档项目：核验目录结构、Markdown 格式、内部引用链接有效性及规则一致性。
4. **交付报告与追溯信息**：核验 `DELIVERY_REPORT.md` 或交付回执是否如实记录基准 Commit SHA、交付状态、已知问题与未完成事项。

## 3. 验收结论四态定义

每次独立验收必须给出以下四种明确结论之一：

| 验收状态 | 判定标准 | 后续动作 |
|---|---|---|
| **通过 (Pass)** | 所有关键验收标准均已满足，交付物完整、证据充分、无阻断性缺陷。 | 向用户汇报验收通过，由用户决定是否合并/归档或开启下一轮任务。 |
| **有条件通过 (Conditional Pass)** | 核心目标已达成且无阻断性缺陷，但存在已记录的非关键瑕疵或环境限制（如部分非核心项需用户本地补充确认）。 | 明确列出遗留项与风险，由用户决定直接接受或要求微调。 |
| **不通过 (Fail)** | 存在实质性功能缺陷、需求遗漏、严重逻辑/规则冲突、越界修改基线或虚假陈述。 | 按问题分级列出具体文件、依据与修复要求，退回 Gemini 返修。 |
| **证据不足 (Insufficient Evidence)** | 交付包不完整、缺少关键文件内容、缺少测试日志/Diff 或无法访问核心交付物，导致无法验证是否达标。 | 明确列出缺失的证据清单，暂停验收结论，要求补充证据后复审。 |

---

## 4. 问题分级与返修处理

- **P0（阻断级）**：违反用户禁止事项、篡改冻结基线、核心功能/文件缺失、编造测试结果或 Commit SHA。出现 P0 必须判定为**不通过**。
- **P1（重要级）**：主要验收标准未完全达标、存在明显逻辑矛盾、失效链接或关键文档缺失。通常判定为**不通过**，特殊情况需用户特批。
- **P2（一般/优化级）**：排版瑕疵、表述可优化但无歧义、非关键细节缺失。可记入**有条件通过**的观察项。

对于 Gemini 提出的基于证据的技术反驳，GPT 须重新核查事实；若确属自身误判应主动更正；若双方仍存重大分歧，须整理双方依据与备选方案交由用户最终裁决。
